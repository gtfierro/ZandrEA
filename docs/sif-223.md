# SIF and ASHRAE 223 Startup Configuration

> **Direction note.** This document describes the *current shipped bridge*
> (generated-SPARQL discovery + the legacy `CTool_*` constructors). The target
> architecture — a new, fully model-driven entrypoint using semantic roles, a
> `zea` inference/profile ontology, and shifty's witness API for extraction — is
> specified and proven in `docs/tool-contract-design.md`. The witness-driven
> approach supersedes the generated-SPARQL discovery layer described below; the
> two known point/connectivity gaps in "Known Gaps" are resolved there. The
> bridge in this doc remains the fallback path and is unchanged.

This document describes the current approach for using an ASHRAE 223 RDF site
model as startup configuration for ZandrEA's SIF/application equipment model.

The implementation is still an early bridge. The important architectural
decision is that ASHRAE 223 parsing, SHACL inference, validation, and model
queries stay isolated in `libEA/s223Model.*`. `libEA/tool.cpp` consumes a small
startup model and remains responsible for constructing the existing tool
classes.

## Goals

- Load an ASHRAE 223 ontology and site model at process startup.
- Run SHACL-AF inference before interpreting the site model.
- Use the inferred graph, not raw Turtle assumptions, to discover equipment and
  relationships.
- Instantiate existing ZandrEA tool classes from discovered equipment.
- Keep the query/semantic mapping layer separate from `tool.cpp` so future
  tool-selection logic can be driven by SHACL shapes.

## Runtime Inputs

Startup loading is enabled by two environment variables:

```sh
export EA_S223_ONTOLOGY_TTL=/path/to/223p.ttl
export EA_S223_SITE_TTL=/path/to/site-model.ttl
```

Both variables must be set together. If neither is set, ZandrEA uses the legacy
default startup configuration.

`EA_S223_ONTOLOGY_TTL` points at the ASHRAE 223 SHACL shapes/rules graph, such
as `https://open223.info/223p.ttl` or a local copy. The loader also reads
`qudt-all.ttl` from the same directory and prepares both S223 and QUDT shapes
together.

`EA_S223_SITE_TTL` is loaded as the RDF data graph for the site.

## Runtime Flow

The runtime entry point is `CApplication::CApplication()` in `libEA/tool.cpp`.

1. `ReadS223ModelLoadConfigFromEnvironment()` checks the two environment
   variables.
2. If no ASHRAE 223 config is present, `tool.cpp` calls `AddDefaultTools()` and
   creates the current fixed AHU/VAV application layout.
3. If config is present, `tool.cpp` calls
   `LoadS223ApplicationStartupModel()`.
4. When built with `EA_HAVE_SHIFTY`, `s223Model.cpp` loads the ontology into
   shifty as shapes/rules and the site model as data. Quad counts for both
   files also come from shifty (`shifty::Dataset::size()`), not a separate
   parse: an earlier revision re-parsed both files with `rdf4cpp` purely to
   count quads, which crashed on real ASHRAE 223 ontology content because
   `rdf4cpp`'s own Turtle parser has a bug unrelated to shifty. `rdf4cpp` has
   been removed from the codebase entirely.
5. shifty validates with:
   - `ValidationOptions::run_inference = true`
   - `GraphMode::Union`
6. After inference, `s223Model.cpp` runs a startup CONSTRUCT query generated
   from the built-in tool profiles and returns an `S223ApplicationStartupModel`,
   which also carries a per-candidate diagnostic report and the site graph
   before/after inference (see below).
7. `tool.cpp` logs the load/validation result, instantiates tools from the
   returned `S223ToolStartupSpec` entries in antecedent-safe order, and stashes
   the full startup model on `CDomain` for later inspection.

The RDF model is used at construction time to populate the normal `libEA`
tool, subject, point, rule, and view/control object graph; after startup,
`EAd` serves the standard application state. The startup result itself
(validation report, site graph before/after inference, and a per-candidate
"why wasn't this creatable" report) is also exposed read-only over REST — see
`docs/s223-debugging-endpoints.md`.

## Current Discovery Rule

Startup discovery is generated from the built-in tool profiles in
`libEA/toolProfile.*`. The generated query runs against the shifty-inferred
dataset and emits a small startup graph containing profile matches, RDF labels,
and antecedent bindings.

The initial built-in profiles use verified ASHRAE 223 terms:

- `s223:AirHandlingUnit`
- `s223:TerminalUnit`
- `s223:SingleDuctTerminal`
- `s223:DualDuctTerminal`
- `s223:FanPoweredTerminal`
- inferred `s223:connectedFrom`, including property paths such as
  `s223:connectedFrom+`

Current mapping:

| ASHRAE 223 discovery | ZandrEA tool |
|----------------------|--------------|
| `s223:AirHandlingUnit` | `CTool_ahu_ibal` |
| any listed terminal unit class | `CTool_vav_ibal` |

For VAV tools, the profile requires an `air_source` antecedent that resolves to
an upstream `s223:AirHandlingUnit`. That relationship is used as the VAV tool's
antecedent AHU when projecting to the current constructor surface.

This is no longer a hand-written AHU/VAV startup query. Adding a new possible
tool should happen by adding a new tool profile, not by editing
`s223Model.cpp` discovery logic.

## Parallel Tool Profile Direction

`libEA/toolProfile.*` is the start of a parallel implementation for the intended
architecture. It does not replace the existing constructors or startup adapter
yet. A tool profile describes the RDF-facing contract for a tool type:

- tool profile id, such as `ahu_ibal` or `vav_ibal`
- S223 focus classes that can satisfy the tool
- required antecedents by role
- required input points by `EPointName`
- SHACL/SPARQL property paths for validation and binding

The important design constraint is that profile matching should be driven by RDF
classes and relationships, not by hardcoded resource names, discovery indexes,
or the current enum slots. For example, the AHU profile targets
`s223:AirHandlingUnit`; the VAV profile targets terminal-unit classes such as
`s223:TerminalUnit`.

Antecedents are also profile requirements, not special-case C++ fields. The VAV
profile has an `air_source` antecedent requirement for an upstream AHU. That
requirement can use a property path such as `s223:connectedFrom+`, allowing a
VAV to bind to an upstream AHU through an inferred distribution path rather than
only through a direct adjacency edge.

`S223PropertyPath` models property paths directly and can render them to SPARQL
or SHACL path syntax. Supported path operators include sequence `/`,
alternative `|`, inverse `^`, zero-or-more `*`, one-or-more `+`, and zero-or-one
`?`.

The profile layer should generate two artifacts from the same definitions:

- SHACL shapes that state the contract for each tool profile.
- SPARQL discovery queries that return RDF resources satisfying those profile
  requirements. Startup discovery requires each creatable tool resource to
  provide `zea:name`.

That generated discovery path replaces the earlier hand-written
`startup_discovery_query()` in `libEA/s223Model.cpp`. In the profile-driven design,
adding a new possible tool means adding a new tool profile; startup then loads
the site model graph, validates the generated shapes, runs generated discovery
queries, and dynamically determines which tool instances can be created from
the data that is present.

The current startup replacement calls
`GenerateBuiltInToolProfileStartupConstructSparql(false)`. The `false` means
RDF point bindings are not yet required in startup discovery because the legacy
constructors still create their own point objects. Focus classes and required
antecedents are dynamic now; point bindings remain the next boundary to move
from constructor code into profile-driven startup. Names come from `zea:name`
in the RDF model; the only remaining legacy step is parsing those model-provided
names into `ERealName` enum slots for current constructors.

## IBAL Example Model

The working example for this direction is described by:

```text
EAd/tests/testdata/ibal-s223-example.json
```

It uses the local `223p.ttl` ontology and the Open223 NIST IBAL site model:

```text
https://models.open223.info/NIST-IBAL.ttl
```

The downloaded local copy is:

```text
EAd/tests/testdata/NIST-IBAL.ttl
```

The local copy carries ZandrEA startup annotations such as `zea:name` for the
data-backed AHU/VAV resources.

This model is intended to align with the existing data mapping:

```text
EAd/tests/testdata/ibal-ahu-vav-column-map.json
```

The example manifest is intentionally discovery-oriented. It does not list
`IBAL:AHU_1` or `IBAL:VAV_1` as selected resources. Instead:

1. Candidate equipment is discovered from the S223 focus classes declared by the
   tool profiles.
2. Subject names come from `zea:name` assertions in the RDF model.
3. The column map filters discovered candidates to the `zea:name` values that
   have data in the EAd test CSV files.
4. Antecedents are bound from the property paths declared by the profiles.

This avoids overfitting the model bridge to known IBAL resource names. For
example, the Open223 model includes `IBAL:AHU_3`; because the current EAd
AHU/VAV column map does not contain `AHU-3`, that candidate should fall out of
the data-backed example by filtering, not by hardcoded exclusion.

## Startup Model Boundary

`libEA/s223Model.hpp` exposes a small C++ boundary:

```cpp
struct S223ApplicationStartupModel {
   S223ModelLoadSummary loadSummary;
   std::vector<S223ToolStartupSpec> tools;
};
```

`S223ToolStartupSpec` contains:

- matched tool profile id, such as `ahu_ibal` or `vav_ibal`
- source RDF resource IRI
- RDF-derived startup name from `zea:name`
- antecedent bindings by role, RDF resource IRI, and discovered name when the
  antecedent is also a matched tool candidate

The `tools` vector is topologically sorted from the profile antecedent graph.
For each matched candidate, `s223Model.cpp` looks up its `ToolProfile`; for
each antecedent requirement, it adds dependencies from required antecedent tool
profile types to the dependent tool. Startup raises an exception if a required
antecedent cannot be matched to the required tool profile type, or if the graph
contains a cycle.

This is deliberately not a general ASHRAE 223 object model. It is a profile
startup adapter from the inferred RDF graph into the new S223-native tool
constructor overloads.

Those overloads currently delegate to the older enum-based constructors. The
S223 path passes the RDF resource IRI as the subject key and `zea:name` as the
display name. VAV antecedents bind to AHUs by RDF resource key, so startup is
not limited to the old fixed `Subject_ahu1`/`Subject_vav1` enum slots.

## Current Limits

The legacy default startup path is still enum-based:

- AHUs: `Subject_ahu1`, `Subject_ahu2`
- terminal units/VAVs: `Subject_vav1` through `Subject_vav4`
- CHW plant: `Subject_chwPlant`
- HW plant: `Subject_hwPlant_sim`

Those enum slots are no longer the S223 instance identity. S223-created AHU and
VAV subjects are dynamically keyed by RDF resource and displayed with
`zea:name`, so a model can create more than two AHUs or four VAVs as long as the
profile requirements and data bindings are present.

The remaining enum references in the S223 AHU/VAV constructor path are fixed
legacy defaults for plant placeholders and compiled subject type labels. They
are not used to identify discovered AHU/VAV instances.

The current C++ shifty API does not expose the Python witness/repair API. From
C++, the available outputs are validation conformance, diagnostics JSON,
validation report Turtle, human-readable validation text, and SPARQL query
results over the dataset.

## Known Gaps (found via the debugging endpoints)

Running the real `NIST-IBAL.ttl` model against the built-in profiles
(`docs/s223-debugging-endpoints.md`) surfaced two mismatches between the
profiles' declared property paths and how this real S223 data actually
expresses the relationships those paths are looking for. Both are the same
shape of problem: a profile path assumes one RDF pattern, the real model uses
a different (arguably more standard-conformant) one, so the path never binds.

**VAV → AHU connectivity.** The `vav_ibal` profile's `air_source` antecedent
uses `s223:connectedFrom+`, expecting SHACL-AF inference to derive
`s223:connectedFrom` edges from the lower-level connection-point network.
Comparing `/s223/graph?inferred=false` against `?inferred=true` shows
inference adds **zero** triples for this model — `s223:connectedFrom` never
appears in either. The real site model expresses physical connectivity via
`s223:cnx` (`ConnectionPoint -cnx-> Connection -cnx-> ConnectionPoint` chains,
hundreds of triples), not `s223:connectsThrough` (zero triples in this
model). Whether the fix is a different/additional inference rule in the
ontology or a property path change in the profile hasn't been determined yet.
Every VAV in the test model reports `creatable: false` with
`blockingReasons: ["missing required antecedent 'air_source'"]` as a result.

**Point bindings don't match the real point-modeling pattern.** Every
`PointRequirement` (`libEA/toolProfile.cpp`, `analog_point()`/
`binary_point()`) uses a flat `s223:hasProperty` path directly from the
equipment resource. The real model instead expresses points via `s223:Channel`
resources typed `Sensor`/`Actuator`, connected to *sub-components* of the
equipment (reached via `s223:contains`, e.g. `AHU_1 contains HeatingCoil_1`)
rather than the equipment resource itself:

```text
HeatingCoil_1 <-hasObservationLocation- Channel_62 -observes-> ahu2_heat_power   (sensor)
HeatingCoil_1 <-actuates- Channel_405 -actuatedByProperty-> ahu2_heat_c          (actuator/command)
```

`s223:hasProperty` never matches this pattern, so `points[].bound` is `false`
for every point on every candidate in this model — not because the data lacks
point information (it has plenty, via `Channel`), but because the profile
paths don't look for it. This is currently harmless only because points don't
gate `creatable` yet (see "Parallel Tool Profile Direction" above); fixing the
property paths is a prerequisite for ever using points as a creation gate,
since gating on the current paths against this data would drop
`creatableToolCount` to zero.

## Build

The container builds install shifty and compile `ead` with `EA_HAVE_SHIFTY`:

```sh
make podman-build
make podman-up
make podman-test
```

The Docker equivalents are also wired:

```sh
make docker-build
make docker-up
make docker-test
```

For local, non-container builds, install shifty into a prefix and pass
`SHIFTY_PREFIX`:

```sh
make compile SHIFTY_PREFIX=/path/to/shifty-prefix
```

See `docs/shifty-s223.md` for lower-level shifty build details.

## Running With A Site Model

With Podman Compose, add the environment variables to the `rest` service or pass
them through the process environment used to create the container. The files
must be readable inside the REST container.

One practical approach is to place the site model under the mounted `data/`
directory and set container paths:

```yaml
services:
  rest:
    environment:
      - EA_S223_ONTOLOGY_TTL=/data/223p.ttl
      - EA_S223_SITE_TTL=/data/site-model.ttl
```

Then rebuild/restart:

```sh
make podman-up
```

Expected startup logs when ASHRAE 223 loading is enabled:

```text
Loaded ASHRAE 223 ontology from ... and site model from ...
Ran ASHRAE 223 SHACL-AF inference and SHACL validation with shifty; conforms: yes
Instantiated N tool(s) from ASHRAE 223 startup model
```

If the model does not conform, startup logs the validation text. If the inferred
graph does not contain the relationships required by the current adapter, the
application fails startup with an explicit error.

## Next Steps

- Define each tool's RDF requirements as SHACL shapes.
- Use profile/shape validation results to select entities for each tool.
- Drive discovery from S223 classes and relationships declared by tool profiles,
  not from hardcoded IBAL resource names or discovery indexes.
- Use RDF labels or configured naming rules for subject names, with data-backed
  filters such as the IBAL column map when running examples against CSV data.
- Fix the `air_source` antecedent path (and/or the ontology's inference rules)
  so `s223:connectedFrom` actually derives from this model's `s223:cnx`
  connectivity network; see "Known Gaps" above.
- Rework point requirement property paths to match the real `s223:Channel`
  (`hasObservationLocation`/`observes`, `actuates`/`actuatedByProperty`)
  pattern, including routing through `s223:contains` sub-components; see
  "Known Gaps" above.
- Extend the startup spec to carry required point bindings, not just equipment
  and antecedent equipment, and decide whether a missing required point should
  block `creatable` the same way a missing required antecedent already does.
- Thread bound RDF point resource identity into the actual `CPointAnalog`/
  `CPointBinary` objects (currently a fixed, compiled-in list per tool type in
  `libEA/tool.cpp`, keyed only by `EPointName`), so downstream data ingestion
  can eventually resolve real device channels from the model.
- Extend dynamic subject identity beyond AHU/VAV to plant and other future tool
  types.
- Keep enum-slot assignment isolated as a legacy constructor compatibility
  projection until constructors no longer require `ERealName` slots.
- Decide whether C++ needs structured witness/repair support from shifty or can
  rely on validation reports and SPARQL query results.
